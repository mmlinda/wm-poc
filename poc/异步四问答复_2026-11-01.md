## 一、防返工补丁 ①：三时间戳（已落库）

`poc/schema.sql` → `wm_batches`：

| 字段 | 何时写 | 用途 |
|---|---|---|
| `queued_at` | 建批次时 `datetime('now')` | 排队起点 |
| `started_at` | Actions **第一次**领任务时写，`IFNULL(started_at, ...)` 保证重试不覆盖 | 排队时长 = `started_at - queued_at` |
| `finished_at` | 回调落 done/failed 时写；**看门狗判死时也写** | `finished_at IS NULL AND 非终态` = 卡死嫌疑人 |

`GET /api/wm/batches/:id` 已经把三个字段一起返回：

```json
{"ok":true,"status":"running","done":0,"total":3,
 "queued_at":"2026-11-01 06:47:36","started_at":"2026-11-01 06:47:41","finished_at":null}
```

> **注意时区**：全部是 SQLite 的 `datetime('now')` = **UTC**。测试断言要按 UTC 解析，
> 别用本地时间算差值（这是最容易写错的断言之一）。

另外为了防"重复提交把库灌满"，加了 `dedup_key`（`u:<admin>:<qq>:<book>` 或 `g:<admin>:<book>`）
和一个非唯一索引 `ix_batches_dedup`，配合**应用层查重**（不用 UNIQUE，因为终态行可以有无数条历史）。

## 二、防返工补丁 ②：故障注入开关（已打通三层）

一条链路三个开关，**默认全关**，生产不设 `ALLOW_INJECT` 就等于没有这个功能：

```
workflow_dispatch.inputs.simulate  →  Worker env.ALLOW_INJECT=1 时才转发  →  Actions 里按值分支
```

| simulate 值 | 注入点 | 期望的可观测结果 |
|---|---|---|
| `none` | — | 正常 done |
| `crash_before` | 领完任务、跑引擎前 `exit 1` | 批次停在 `running`，`finished_at` 为 NULL → **必须靠看门狗转 failed** |
| `crash_after` | 引擎跑完、回调前 `exit 1` | 同上；但 R2 里可能已有半成品（可被清理任务回收） |
| `no_callback` | 跑完但跳过回调 | 同上（模拟网络断/回调 502） |
| `turso_fail` | 回调到达 Worker，Worker **故意返回 500 且不写库** | 状态**不得**变 done；仍停在 running → 看门狗收敛 |

本地已实测（`poc/local_run.mjs` 第 ⑨ 项）：
`POST /internal/callback {simulate:"turso_fail"}` → `HTTP 500`，且库里 `status` 仍是 `running`。

**PoC 阶段没有做的**：注入只覆盖"任务级"。**没有**做"Turso 整体不可用""R2 写入失败"的注入——
那两个要到真环境用错误凭据跑一次（QA §3.4 CONS-002 的第二种手段），PoC 先不做。

## 三、防返工补丁 ③：看门狗（僵尸清理）—— 已实现，等你们来打

`POST /internal/watchdog`，头 `X-Watchdog-Token: <env.WATCHDOG_TOKEN>`（没配就一律 403）：

```json
// 请求（body 可省，省了用环境变量）
{"minutes": 20, "queue_minutes": 30}
// 响应
{"ok":true,"killed":2,"ids":["..."],"stuck_minutes":20,"queue_minutes":30}
```

判定逻辑（**先查后改**，一次最多 50 条，避免一次写爆 Turso）：

```sql
SELECT id,status FROM wm_batches
 WHERE (status='running' AND updated_at < datetime('now', ?))   -- 默认 -20 minutes
    OR (status='queued'  AND updated_at < datetime('now', ?))   -- 默认 -30 minutes
 LIMIT 50;
-- 然后逐条：status='failed', failed=failed+1, reason='watchdog: ...', finished_at=now()
```

为什么用 `updated_at` 而不是 `started_at`：running 期间只要有进展就会刷新 `updated_at`，
而 `started_at` 是"第一次开跑"的锚点，用它判死会误杀长任务。

**测试怎么造僵尸**（不用等 20 分钟）：
```bash
# 1) 扔一个 crash_before 的任务，让它停在 running
# 2) 直接把时间拨回去（真库也能改，PoC 库是 Turso，用 shell 或 pipeline 都行）
UPDATE wm_batches SET updated_at=datetime('now','-2 hours') WHERE id='<batch>';
# 3) 触发看门狗
curl -X POST $WORKER/internal/watchdog -H "X-Watchdog-Token: $T" -d '{"minutes":1}'
# 4) 断言 status=failed 且 finished_at 非空
```

**还没做的（要你们在 W3 之前提，我按需加）**：
1. **告警**：判死后只改库，没发通知。生产要接一个 webhook。
2. **自动重试**：判死即失败，不自动重跑。要不要重试是产品决策（重跑会改变 watermark_id）。
3. **R2 半成品回收**：`crash_after` 会在 R2 留一个没人引用的对象，目前只能靠保留策略扫。
4. **调度**：看门狗是**接口**不是定时器。生产由 Cloudflare Cron Trigger 每 5 分钟打一次
   （PoC 没建 Cron，因为要 wrangler 配置）。

## 四、四问的正面回答

### Q1 幂等性：同一件事做两次，会发生什么？

分三层，每层行为不同 —— 这直接决定用例怎么写：

| 场景 | 现在的行为 | 断言口径 |
|---|---|---|
| **领取端连点 5 次**（`POST /api/claim` 同一人同一书） | 第 1 次建批次，后 4 次命中 `dedup_key` + `status IN ('queued','running')`，**返回同一个 `batch_id`**，并带 `"dedup": true` | `batch_id` 全等；库里 `dedup_key` 的在飞行 **= 1** |
| **Actions 重复回调同一批次** | 第一次落库并置终态；之后一律 `{"ok":true,"idempotent":true,"status":"done"}`，**不改库** | 连续 3 次回调后 `done` 计数不变、`finished_at` 不变 |
| **同一批次被重复 dispatch** | Workflow 有 `concurrency: wm-poc-<batch_id>` → 第二个 run 会**排队等第一个**；等它跑到领任务时，token 已被 nonce 消耗 → `409 token reused` → 任务空跑结束 | 不会产生第二份成品；`files` 表仍 1 行 |
| **同一任务重跑（人工重试）** | 目前**没有"重试"接口**。要重试就新建批次 → 新的 `watermark_id` → `files` 中 `(admin,qq,book)` 被 upsert 覆盖 | 旧水印仍留在 `wm_mapping`（可溯源），但人只拿到最新那份 |

**结论给测试**：幂等 = "**不会产生第二份数据**"，不等于"**开销为零**"（重复 dispatch 仍会烧一次
runner 时间，因为那一步发生在领任务之前）。

### Q2 僵尸清理：`running` 卡住谁来收尸？

见第三节。要点三条：
1. **有看门狗**，判据 `updated_at`，默认 running 20 分钟 / queued 30 分钟，可被请求体覆盖（测试用 1 分钟）。
2. **判死不改数据只改状态**：`wm_mapping` 里已经写进去的映射**不删**（删了就是丢溯源，比 failed 更糟）。
3. **槽位释放**：Concurrency 是 GitHub 侧的，看门狗改库并不会 cancel 那个 run。
   如果 run 其实还活着、只是慢，那它还可能回调回来 —— 此时回调会因为"终态不可变"被吞掉（幂等返回）。
   **这是可接受的**：迟到的成功不会把 failed 改回 done，代价是这一份成品要重发。要不要"迟到成功改判"是产品决策，我倾向不改（终态不可变更安全，测试也好写）。

### Q3 下载链接时效：链接会过期吗？会被串号吗？

Token 结构：`base64url(purpose|scope|exp) + "." + HMAC-SHA256(CB_SECRET, ...)`，**无状态**（不查库）。

| 项 | 现在的值 | 怎么改 | 测试建议 |
|---|---|---|---|
| 有效期 | **300 秒**（`env.DL_TTL` 可覆盖） | 设 `DL_TTL=5` 就能真测过期，不用等 5 分钟 | 签完睡 6 秒 → 必须 403 |
| 绑定 | `scope = R2 对象 key`（**本轮刚修的漏洞**：之前 scope 是空串，拿母本的 token 换个 `k` 就能下成品） | — | 拿合法 token 把 `k` 换成别的对象的 key → 必须 403 |
| 次数限制 | **没有**。链接在有效期内可无限次下 | 要做就得引入 nonce/jti 落库（现在是纯无状态，加不了） | 别写"第 N+1 次 403"这类用例，现在一定红 |
| 撤销 | **没有**。发出去的链接只能等它自己过期 | 同上 | — |
| 重新领取 | 每次 `claim` 都签**新**链接，旧链接在到期前**仍然有效**（不互斥） | — | "刷新页面后旧链接失效"这条现在不成立 |

**为什么不做 Presigned URL**：PoC 用 Worker 代理 + 短期 token（安全性等价，都经 Worker 校验），
省掉 80 行易错的 SigV4。代价是吃 Worker 请求数（免费 10 万/天）。
生产要换 `aws4fetch` 生成真 presign 时，**上面那张表除了"有效期"以外都不变**（presign 也不支持限次/撤销）。

### Q4 排队超时后落库：用户跑了，数据还写不写？

**写。** 三条硬规则：

1. **Turso 是唯一事实来源，客户端行为不影响写库**。用户 5 分钟关页面，Actions 照跑、回调照写、
   `wm_mapping` 照落。这是异步架构和同步架构最本质的区别，也是"僵尸完成"（QA R3）的根源。
2. **"僵尸完成"不阻断任何东西，只浪费 R2 空间**。所以对策不是拦截它，是：
   - `files` 表登记了，用户**下次点同一本书直接秒下**（不需要重新排队）——这就是预生成的价值；
   - R2 靠**保留策略**定期回收（旧架构那套 `ret_on/ret_hours` 要一起迁过来，别丢）。
3. **客户端超时 ≠ 任务取消**。前端不能显示"失败"，只能显示"还在准备，可以稍后再来"。
   PoC 里 `claim` 未命中时返回 `{ready:false, batch_id, eta:180}`，**eta 是我给的估算不是承诺**，
   前端文案不要写死"3 分钟"。

**对账（QA §3.4 的三元组）现在能做的**：`batch_id → (Turso 状态, wm_mapping 行, R2 对象)`。
`files` 表在回调成功时自动写入（`ON CONFLICT(admin_id,qq,book_id) DO UPDATE`），所以
`status=done` ⟺ `files` 有行 ⟺ R2 有对象 —— 三者可以在测试里直接对。
